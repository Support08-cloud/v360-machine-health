# V360 Machine Health Audit System — Handoff Spec

## What this is

V360 Technetronic LLP manufactures diamond video-scanning machines (the "B2B mini" line,
currently at 4.0 and 5.0, with a 5.0 EDF variant). Diamond manufacturers who own fleets of
these machines — the reference customer throughout this spec is **Harikrishna Export**, a
14-machine fleet — periodically need their machines audited against a calibrated reference,
both to catch drift/faults and to build a case for maintenance or upgrade.

This system has two halves, built and tested separately, meant to connect through a shared
JSON handoff:

1. **The Report Generator** (`reference_implementation/v360_report_generator.html`) — a
   salesperson-facing tool. It takes customer details and four folder selections (an ideal
   reference, the customer's own machines, and two optional upgrade-comparison tiers),
   reads the real folder structure in-browser, and produces a `manifest.json` describing what
   it found.
2. **The Machine Health Report** (`reference_implementation/v360_machine_health_demo.html`) —
   the actual audit report. Fleet-wide summary and ranking, per-machine drill-down, per-stone
   color/quality/correction comparison against the ideal reference, auto-generated diagnosis
   and recommended fixes, full English/Gujarati bilingual support, four visual styles, and
   three audience modes (Manufacturer / Salesperson / Engineer) with granular section
   toggles underneath each.

**The one thing this spec set is explicit about: the Report currently runs on simulated data.**
Six sample machines with hand-picked scores, and per-stone color/sharpness/contrast/correction
numbers generated by a seeded pseudo-random function anchored to real reference values (not
computed from actual images). The UI, the interaction design, the scoring model, the diagnosis
logic, the brand system, and the bilingual layer are all real and tested. What's missing is the
pipeline that reads real capture files (the ones the Generator's folder detection finds) and
turns them into the real numbers the Report already knows how to display. That pipeline is the
next piece of work, and it's scoped in `08_current_state_and_next_steps.md`.

## How to read this spec set

Read in this order if you're implementing:

| File | Covers |
|---|---|
| `01_architecture.md` | The whole system end to end — audit scenario, data flow, folder conventions |
| `02_input_tool_spec.md` | The Generator: every screen, every field, the detection logic, the manifest schema |
| `03_output_report_spec.md` | The Report: every section, every interaction, the theming and audience systems |
| `04_data_model_and_capture_schema.md` | The real V360 capture JSON schema, and the manifest schema |
| `05_scoring_algorithm_spec.md` | Every formula — what's simulated today and what it needs to become |
| `06_brand_guideline_reference.md` | Colors, type, logo — condensed from V360's own brand package |
| `07_localization_spec.md` | The EN/GU system, and how to add a third language |
| `08_current_state_and_next_steps.md` | Honest status: real vs. simulated, and the concrete next build |
| `09_file_manifest.md` | Everything in this zip, in one place |

`reference_implementation/` holds the actual working HTML files this spec describes — open
them directly in a browser, they run standalone with no server or build step.

## Ground truth this spec is built from

Everything here traces back to real files reviewed during this project, not assumption:
a real "Diamond Settings Record" PDF from a live V360 machine, a real capture JSON schema
(`visionProfile.currentProfile` / `lockedProfile`, `OldRGB`/`NewRGB`, full camera/lighting
settings), V360's own brand guideline package, and hands-on testing of both tools against
real on-disk folders and real images — not just code review. Where a number or format is
copied from a real sample, this spec says so. Where something is a reasonable default
invented for the demo, it says that instead.
