# Current State & Next Steps

## What's real and tested

- **Folder detection** (Generator) — genuinely reads real folder structures via the browser's
  File API, handles both naming conventions found in real samples, tested against real
  on-disk folders and real images in a real browser (not just unit-tested in isolation),
  including a pixel-level check that multiple machines sharing identical stone-folder names
  never cross-contaminate.
- **Manifest generation** — real, working, produces the exact JSON documented in
  `04_data_model_and_capture_schema.md`.
- **The entire Report UI/UX** — every section, every interaction, all four visual themes, the
  audience/visibility system, save/persistence, both languages — built and tested (Node
  execution tests across all 6 sample machines × both languages × multiple settings
  combinations, plus real-browser click-through tests for the interactive flows).
- **The composite-scoring formula, diagnosis logic, and recommended-fix logic** — these are
  real algorithms operating on whatever numbers they're given; they do not need to change
  when real numbers replace simulated ones, only the numbers feeding them do.
- **The correction-load anchor value** (`18`) — a real number, averaged from two real
  captures' actual `OldRGB`→`NewRGB` distances, not invented.
- **Camera-setting ideal values** (`Sharpness: 7`, `Contrast: 0`, `AV: 9`, etc.) — real values
  observed in actual capture samples, not invented, though currently applied as one shared
  set across all 6 stones rather than read per-stone from a real ideal-reference folder.

## What's simulated

- **The 6 sample machines' scores** — hand-picked numbers chosen to tell a coherent,
  varied demo story (one clearly healthy machine, one clearly failing, each of the 5
  sub-metrics gets to be the "weakest area" for at least one machine). Not derived from any
  real capture.
- **Per-stone color/quality/correction numbers** — generated by a seeded seudo-random
  function anchored to the machine's overall score and to real reference constants (see
  `05_scoring_algorithm_spec.md` for exactly which function produces which number) — stable
  and reproducible, but not read from real images or real JSON.
- **The 6 master stones' shapes** — only `D-4` = Princess cut is confirmed against a real
  reference photo; the other five shape labels are invented for demo variety.
- **`MACHINE_META_OVERRIDES`** — a hand-authored dict of "which setting is wrong on which
  machine," designed so the demo's diagnosis and recommended-fix text has something concrete
  to report. A real pipeline replaces this with an actual field-by-field diff.

## The next build: the Capture Processing Pipeline

This is the piece that turns the manifest into real report data. Scoped, not built.

**Input:** `manifest.json` (from the Generator) plus direct read access to the same folders
the Generator detected (the manifest has paths and identifiers, not file contents).

**For each machine, for each of its detected stones:**
1. Read that stone's `0.json` from the customer-machine folder, and the *same stone number's*
   `0.json` from the ideal-reference folder (and, if present, from the 5.0 / 5.0 EDF folders).
2. Compute the 5 base metrics per stone using the real-data formulas in
   `05_scoring_algorithm_spec.md` — color (RGB/Lab distance), picture quality (sharpness/
   contrast setting match), consistency (background-patch stability), correction load
   (`OldRGB`→`NewRGB` distance, direct parse), speed (`TotalTime` comparison).
3. Aggregate the 6 stones' worth of per-metric readings into one 0–100 score per metric per
   machine — **the exact aggregation/normalization curve (what raw distance maps to what
   score) is not decided yet** and is the single biggest open design question in this whole
   handoff. It likely wants calibration against known-healthy and known-faulty real machines
   rather than being picked arbitrarily.
4. Emit one `{id, scores:{color,picture,consistency,correction,speed}}` object per machine —
   `composite` is computed automatically by the Report itself, not by the pipeline.

**Output:** a `machines` array in exactly the shape documented in `03_output_report_spec.md`,
which drops into the Report's existing `var machines = [...]` with no other code changes
required.

**Secondary, lower-priority items**, each independent of the pipeline above:
- Wire the Report's "visual compare" thumbnail/full-video toggle to real `still.jpg` /
  `video.mp4` files (currently colored placeholder chips) — this is a rendering change only,
  no new logic, similar to how the Generator already renders real thumbnails.
- Decide how the pipeline should handle an incomplete machine (a customer machine missing
  some of its 6 stones) — skip it, flag it in the report, or score it on partial data. Not
  decided in this project.
- A native desktop wrapper (Electron, or a local backend) if true cross-platform folder
  access is needed beyond what a browser's directory-picker input provides — see the
  "Browser support" note in `02_input_tool_spec.md`.
